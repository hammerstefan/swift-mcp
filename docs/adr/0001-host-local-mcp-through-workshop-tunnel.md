# Keep Swift credentials on the host and connect container Workshops through an authenticated MCP endpoint

Status: accepted for planning; authentication component must pass security review before deployment.

The MCP server will run on the same host as a container Workshop and retain the Swift credentials there. OpenCode and Copilot CLI inside the Workshop will use Streamable HTTP through a manually connected Workshop tunnel. Native stdio inside the Workshop would require making Swift credentials available in its trust boundary; a raw Unix-socket or stdio bridge through a tunnel would not authenticate individual callers. A host-local HTTP endpoint is therefore acceptable only when an established authentication component validates each request, including resource reads, and the listener remains restricted to loopback.

The preferred one-process design is a **maintained, independently reviewed Python ASGI API-key authentication component**, with a separate revocable key for each Workshop. No component has been approved yet. If none meets the review criteria, use FastMCP's GitHub OAuth proxy with an operator-configured allowlist of stable GitHub user IDs; do not silently serve unauthenticated or use its development-only static-token verifier for real Swift access. A gateway-managed API key, restricted SSH stdio, and a separately operated OAuth provider remain alternatives if the selected designs fail integration tests.

Consequences: Workshop tunnels do not provide authentication, and a connected Workshop secret is available to other processes in that Workshop. The primary design avoids an additional identity service but must establish secure key provision/rotation, streaming-compatible request authentication, rate limiting, and fail-closed startup. The GitHub fallback requires registering an OAuth App and a real-browser/client interoperability check. This decision covers container Workshops only; Workshop VM tunnels are unavailable.
