# Swift read-only MCP server — planning contract

Status: implementation in progress; see `docs/conformance.md` for selected fixture results. This document records the original planning contract, not release approval.

## Goal and boundaries

Build a Python project managed with uv, linted/formatted with Ruff, and checked with ty. Use FastMCP v4 on the MCP Python SDK v2. The service runs on the host that also runs a **container** Workshop. OpenCode and GitHub Copilot CLI in the Workshop connect over a manually connected host-service tunnel to a loopback-only Streamable HTTP endpoint. Workshop VMs, a network-exposed listener, uploads, metadata changes, deletes, copies, TempURL generation, and historical object versions are out of scope.

The supported MCP revisions are **2025-11-25 and 2026-07-28**. FastMCP v4 serves both; test each on its own wire format. A real OpenCode and Copilot CLI connection is a release gate, not evidence supplied by library compatibility alone. In particular, Copilot CLI has an [open modern/legacy handshake issue](https://github.com/github/copilot-cli/issues/4888); do not claim it works until tested with the installed client version.

## Data model and MCP contract

- One operator-provided Swift identity supplies the view for all authenticated MCP callers; no caller impersonation or per-user Swift credentials. Swift permissions remain authoritative. Optional exact-name container allowlist: **unset = all readable containers**, **explicitly empty = deny all**, **nonempty = named containers only**. Enforce it on every list, stat, tool read, and resource read.
- Tools: account statistics, paged container list, container statistics, paged object list, object statistics, and bounded object read with explicit byte offset and length. Use only `Connection.head_account`, `get_account`, `head_container`, `get_container`, `head_object`, and `get_object` or equivalently restricted GET/HEAD operations; never expose arbitrary Swift headers, query strings, URLs, or general-purpose request methods as tool parameters.
- Listings return at most one page with a continuation marker; support Swift-native prefix and delimiter where applicable. While a container allowlist is configured, the container list is paged from the allowlist itself, not from the account, so neither entries nor markers can expose an excluded container (ADR 0002). Stream and bound listing JSON responses (default **4 MiB**, configurable) because swiftclient's list methods buffer the complete response body. Do not fetch full listings or perform cross-container scans. Default page maximum: **1,000 entries**.
- Object reads default to **1 MiB maximum per call**. Operator may configure any positive finite read/page limit; there is deliberately **no non-overridable ceiling**. Apply finite timeouts, bounded concurrency and request-rate controls, enforce the configured limit on bytes actually read even if Swift ignores a Range request or an object changes after HEAD, and close partial streams safely. An oversized request is an error, not an unbounded download.
- Return strict UTF-8 for recognized textual content; return lossless base64 with content type, size, offset and partial-result indication for binary or invalid text. Validate and encode names and URIs; never interpret Swift names as local filesystem paths. Return only reviewed, non-sensitive metadata fields (for example byte count, content type, timestamp and ETag); never return raw account/container/object headers or TempURL/signing keys.
- Expose read-only object **resource templates**, not an enumerated account-wide `resources/list`. A resource read returns the whole object only if within the configured maximum; otherwise it errors and points to the ranged read tool. Apply the same authentication, allowlist, byte limit and metadata policy as tools.
- Treat object content and metadata as untrusted data, not instructions. Errors shown to a caller are safe and bounded; internal logs may carry diagnostic IDs but never credentials, tokens, object bytes or secret-bearing headers.

## Authentication and configuration

There are **two different credential boundaries**: (1) the host server authenticates to Swift using documented swiftclient environment variables; (2) a Workshop client authenticates to the host MCP endpoint. A Workshop tunnel, host loopback address, Unix socket or file permissions alone do not authenticate the MCP caller.

Swift v1 scope is Keystone v3 password login (`OS_AUTH_URL`, `OS_USERNAME` or `OS_USER_ID`, `OS_PASSWORD`, project and user domain/project variables, and a v3 auth-version setting) plus the documented pre-issued `OS_AUTH_TOKEN` + `OS_STORAGE_URL` pair. Support appropriate swiftclient environment-based region, endpoint and certificate settings after verifying their exact mapping. Reject absent/incomplete or simultaneously complete password and pre-issued-token modes rather than silently choosing one. Keystone v1/v2 and `clouds.yaml` are not in scope. Use swiftclient's `Connection` for its supported authentication/retry behavior; a pre-issued token has no password credentials with which to re-authenticate, so its replacement remains the operator's responsibility. Preserve the CLI's explicit `SWIFTCLIENT_INSECURE` opt-in, but verify TLS by default and surface a prominent warning when verification is disabled; never silently disable it.

For host MCP access, **first research a maintained Python ASGI API-key component** compatible with FastMCP's streaming HTTP app. Selection is a blocker, not a license to implement custom authentication. It must: fail startup when no keys are configured; deny missing, invalid and revoked keys on every data request; avoid public-path pattern bypasses and timing-leaky comparisons; accept header-only keys; support separate revocable Workshop identities and rotation; not buffer SSE/streaming responses; and have an audited way to load secrets from a secret manager without logging or committing them. Add per-key rate limits and bounded concurrent requests. Keep the listener loopback-only and explicitly allowlist legitimate Host/Origin values to prevent DNS rebinding. Workshop's secret connection must be manual; its connected secret is accessible to other processes in that Workshop. Document this exposure and give each Workshop its own key.

Research note: FastMCP's own `StaticTokenVerifier` is documented for development/testing, not real-data production use. The examined [`fastapi-key-auth` middleware](https://github.com/iwpnd/fastapi-key-auth/blob/main/src/fastapi_key_auth/middleware/authorizer.py) uses ordinary string equality for keys and supports regex-matched public paths, so it is **not** an approved component for this plan; reassess against its current code if that changes.

If no suitable component passes review, **switch to FastMCP's GitHub OAuth proxy**, not an unauthenticated/dev-only API-key mode. Require a GitHub OAuth App, secure storage for its client secret, and a nonempty allowlist of stable GitHub user IDs; an arbitrary GitHub login is not permission to read Swift. Verify the callback and login flow through the host/Workshop tunnel with both clients, including token refresh/restart behavior. No local OAuth login server will be written for this project. If the fallback also fails, stop and seek a new design decision.

The operator may supply an existing Swift identity that also has write privileges, though the server itself has no write operation. Prefer a genuinely read-only Swift identity in deployment; document the higher impact of a compromised host process otherwise. The combination of **unset container allowlist + broad Swift credentials + insecure TLS opt-in + operator-raised output limits** increases exposure and must not be hidden in defaults or documentation.

## Verification gates, not claims of passing

1. Review the chosen auth component and secret-delivery design against the conditions above. Validate the specific versions of FastMCP, swiftclient, Python, uv, Ruff and ty before freezing dependencies; target Python 3.11+ unless a selected dependency requires newer.
2. Unit/contract-test both Swift credential modes, ambiguous/missing environment, TLS verification, pagination and marker handling, allowlist unset/empty/nonempty, URL/name encoding, current-version-only reads, byte-range enforcement when HEAD and GET disagree, invalid UTF-8, MIME mismatch, metadata redaction, failures and resource/tool parity. Use a fake Swift endpoint or recorded protocol fixtures without real secrets. Exercise 401/403/429 and access denial on **every** exposed MCP route.
3. Use a separate **credential-free, loopback-only conformance fixture** built on the same MCP stack for the upstream suite's fixed sample tool/resource names. Production must never register those fixture handlers. Pin the conformance runner revision, record the exact applicable server scenario/check IDs, and execute scenarios against **each** dated protocol revision independently; do not baseline away failures. The runner's full server suite asks for unrelated audio, image, prompt and interactive sample features. Passing a selected capability-relevant matrix is not the same claim as passing its entire default suite.
4. Separately integration-test real Swift tools/resources against a controlled Swift service; run Ruff, ty and Python tests in CI. Smoke-test the host HTTP endpoint through an actual container Workshop tunnel with OpenCode and Copilot CLI at recorded versions. If the configured auth path or Copilot 2026/legacy negotiation fails, the release gate fails rather than weakening auth or changing wire formats silently.
